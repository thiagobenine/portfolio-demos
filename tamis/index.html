Page for what’s broken. Count what’s expected.

If your team hears about incidents from customers, every error probably looks the same. Tamis sets up structured logs, splits errors into expected and unexpected, and wires dashboards and alerts into the stack you already run.

Book a setup How errors get sorted
UNXUnexpected: pulled out of line, someone looks now.
EXPExpected: stays in line, counted, nobody is paged.

A declined card is not an incident.

Every error type in your code gets a class, decided with your team, one type at a time. Unexpected errors page a person. Expected errors are counted and charted, and only alert when their rate moves. The status code does not decide it: some 5xx are expected, and some 4xx are your bug.

Unexpected: someone looks now

4 types in this example
  • UNX upstream_timeout504 psp-client: context deadline exceeded after 2000ms POST /v1/charges Pages on-call
  • UNX null_reference500 TypeError: Cannot read properties of undefined (reading 'amount') POST /v1/refunds Pages on-call
  • UNX db_pool_exhausted503 timeout acquiring connection: 20 of 20 in use GET /v1/orders/{id} Pages on-call
  • UNX signature_clock_skew401 webhook signature timestamp outside 300s tolerance (skew 312s) POST /v1/webhooks/psp Pages on-call

A 401 that is our bug: the server clock drifted, so valid webhooks fail signature checks.

Expected: counted, nobody is paged

  • EXP order_not_found404 order ord_91XK was deleted by the customer GET /v1/orders/{id} Chart only
  • EXP idempotency_conflict409 Idempotency-Key reused with a different request body POST /v1/charges Chart only

A 503 we were told about in advance. Chart it, show it on the status page, do not wake anyone.

One request, followed across every service.

Every log line is JSON with the same fields in every service. The trace context travels in the W3C traceparent header, so the lines from the gateway, the API and the payment client open as one trace. Sensitive fields are filtered before the line is written, not masked later in the log store.

Filtered before the line is written

The filter runs inside the logger, with tests in your CI. The list is reviewed with you and lives in the guide.

Pages for broken, not for busy.

Five rules to start. Each one says who gets told and how, waits long enough to ignore a blip, and links to its runbook section in your guide. Expected errors never page on their own; only a change in their rate earns a message.

  1. PAGE

    Unexpected error rate

    sum(rate(http_errors_total{class="unexpected"}[5m])) / sum(rate(http_requests_total[5m])) > 0.02

    for 5 min, on-call pagerReal users are hitting a bug right now.runbook: guide, section 3.1

  2. PAGE

    Error budget burn

    burn_rate(slo="availability-99.5", window="1h") > 14.4 and burn_rate(slo="availability-99.5", window="5m") > 14.4

    both windows, on-call pagerAt this pace the month's error budget is gone in about two days.runbook: guide, section 3.2

  3. PAGE

    Checkout latency

    histogram_quantile(0.99, sum by (le) ( rate(http_request_duration_seconds_bucket{route="POST /v1/charges"}[10m]))) > 1.2

    for 10 min, on-call pagerSlow enough at the 99th percentile to lose orders.runbook: guide, section 3.3

  4. CHAT

    Expected, but not at this rate

    rate(http_errors_total{code="card_declined"}[15m]) > 3 * avg_over_time(card_declined:rate15m[7d])

    for 15 min, payments channelDeclines are normal. Three times the weekly baseline usually means the provider has a problem.runbook: guide, section 3.4

  5. NEVER

    Any single 4xx

    http_errors_total{status=~"4.."}

    no alert, chart onlyMost 4xx are clients sending bad requests, so a single one never pages. The 4xx that are our bug, like the clock-skew 401, are classified unexpected and page through the first rule.

What gets installed, and what you keep.

A fixed list, built in your repositories through pull requests your team reviews. Nothing runs on our side after handover.

  • Log schemaOne JSON shape for every service: ts, level, service, route, status, duration_ms, request_id, trace_id, span_id, error.class, error.code.
  • Redaction filterRuns inside the logger for each language, with tests, and the list of fields it drops.
  • Error classification mapEvery error type in your code marked expected or unexpected, reviewed with you, enforced where errors are raised.
  • Trace propagationW3C traceparent across HTTP calls, queues and background jobs, through an OpenTelemetry SDK.
  • Three dashboardsError rate split by class, latency p50, p95 and p99 per route, traffic per route.
  • Alert rulesThe five above, tuned to your routes and objectives, each linked to a runbook section.
  • A short written guideHow to add a field, classify a new error, silence a noisy rule and change a threshold.
